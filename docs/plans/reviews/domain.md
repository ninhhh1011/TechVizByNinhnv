## P1-T3 and gate recommendation

The rubric separates content correctness, learner understanding, accessibility and performance, names assessors, records evidence, and treats a semantic error as a failure. Its proposed p95 threshold and five-person pilot still need owner approval; no pilot result or measured POC threshold is evidence here. `node docs/plans/phase1/check.mjs` passed (11/11 fixture structure and selected arithmetic) and `node --test src/services/scenarioContract.test.mjs` passed (8/8). Those results do not turn the prose negatives into tested fixtures or independently certify every oracle frame.

**G0: hold pending the other gate evidence.** The Master Plan requires reproducible build/smoke, expected traces, rubric and triaged defects. P1-T2 has the required positive/negative *table*, and its claim limits are appropriate; executable negative fixtures belong to P3-T2. This review supports the limited positive oracle examples and S1/S2 arithmetic, but P1-T1 still needs two independent expected-state reviews and P1-T3 needs owner approval of thresholds/pilot. The domain review alone cannot attest P0 build/smoke or backlog approval. Do not use this draft to authorize P2 solely on an 11/11 structural check.

**P3: treat current work as a protective boundary, not a completed domain validator.** Keep valid unreviewed AI `unsupported` and malformed AI `error`; keep legacy preset acceptance labeled as compatibility only. Before calling a capability `verified-simulation`, add a deterministic runner or independently reviewed oracle plus a failing negative for each applicable semantic invariant, then test replay/seek and claims. A1 has the first narrow runner; array search, grid, flow, tree and fitness do not yet have comparable P3 semantic evidence.

## Targeted P3-T2 scope audit (2026-10-22; supersedes the broad P3 recommendation above)

`MASTER_PLAN.md` says **“validator invariant theo capability; reference runner/trace cho case deterministic đầu tiên”** and requires step-by-step oracle, property tests, a failing fixture for each invariant, and no acceptance without sufficient source. It does **not** require semantic validators for every family at P3-T2. P4-T2/T3 explicitly schedule array/grid and flow/tree/swarm mapping and their additional invariants; P4-T1 schedules playback determinism. P5-T1/T3/T4 schedule capability routing, LLM false-acceptance evaluation and human review. My earlier statement that all five families need comparable P3 semantic evidence before P3-T2 can pass was too broad.

**Verdict: P3-T2 meets the stated requirement for the currently implemented A1 capability, with a wiring limit.** `bubblePass` is the first deterministic runner; its arrays match every A1 oracle frame and property tests cover 27 three-element inputs. `validateBubbleTrace` derives the required initial/compare/swap sequence from the input and rejects wrong event order, changed compare state, corrupt swap state and a missing frame; the new test exercises all four failures and the valid A1 trace. `node --test src/services/scenarioContract.test.mjs` now passes **9/9**. These are the applicable event/array negatives for the A1 one-pass capability; tree, grid, flow and fitness invariants are inapplicable to that capability.

The accepted paths are narrow: `parseCandidate` returns `error` for malformed AI input and `unsupported` for every structurally valid AI proposal; `groq.ts` only returns that result. `adaptPreset` returns `accepted` with `source: 'legacy-preset'` and the same scenario/steps references, as its test asserts for all 11 presets. `validateBubbleTrace` is currently called only by tests, not by either accepted path. This is **not** a false acceptance of new AI, and the identity adapter does not purport to certify legacy semantics. It does limit what “validator” means operationally: no live A1 proposal can be accepted through it yet. Wire the validator into a future A1 acceptance route before enabling that route; do not describe legacy acceptance as semantic verification.

Thus the remaining domain gaps above are a roadmap for newly enabled capabilities, not blockers to this scoped P3-T2 result. G0/G1 gate approval and the separate P3-T3/T4 acceptance criteria still need their own evidence; this audit does not decide them.
